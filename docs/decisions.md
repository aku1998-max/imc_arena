# Decisions and defaults

Record of the defaults and interpretations chosen while implementing the V1 specification.
"Spec" means _IMC Arena System Specification v1.0_ (25 September 2026). Product values are
configurable defaults in `packages/domain/src/config.ts` unless noted.

## Blocking contradictions

None found. The items below are interpretations of ambiguous points, not blockers.

## Decisions

| ID    | Decision                                                                                                                                                                                                                                                                                                                                                                                              | Rationale / spec reference                                                                      |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| D-001 | pnpm monorepo exactly as spec §04. Internal packages are consumed as TypeScript source; API and worker bundle with esbuild.                                                                                                                                                                                                                                                                           | Keeps one toolchain; no publish step.                                                           |
| D-002 | Runtime DB role is fixed as `imc_api`; migration/owner role `imc_owner` has `BYPASSRLS` so SECURITY DEFINER routines can recheck ownership themselves. `imc_api` is never owner, superuser or BYPASSRLS (tested).                                                                                                                                                                                     | §05/§08: migration identity differs from runtime identity.                                      |
| D-003 | Request context uses `set_config('app.principal_type'/'app.account_id'/'app.student_id', …, true)` inside `BEGIN…COMMIT` on one connection (`packages/db/src/context.ts`). Missing context → no rows. Principal types: `child`, `adult`, `staff`, `system` (worker/webhooks), `anonymous` (pre-auth token lookup only).                                                                               | §08.                                                                                            |
| D-004 | Answer keys: no grant on `private` for `imc_api`. Access only via `app.grade_item` (child, own pending item in active session, option must be a choice), `app.revealed_answer_key` (after an attempt; child or guardian) and staff functions.                                                                                                                                                         | §08 "narrowly scoped grading function".                                                         |
| D-005 | Staff roles: `editor`, `reviewer`, `administrator`, `support`. Administrators can draft, review others' versions and publish; nobody can approve their own version (API check + DB `CHECK (approved_by <> author_id)`). Support/editors see reports; content roles never see student records.                                                                                                         | §05.                                                                                            |
| D-006 | Content hash = SHA-256 of canonical JSON of grade, topic, difficulty, key and all localizations. Approval stores it; publish recomputes it. Any edit after approval returns the version to draft.                                                                                                                                                                                                     | §09.                                                                                            |
| D-007 | Publishing a correction retires the previously published version of the same question (one published version per question, unique index). Retired versions stay readable for existing attempts.                                                                                                                                                                                                       | §09.                                                                                            |
| D-008 | Wrong-key retirement (`flagAffectedResults`) enqueues a system job that abandons active sessions still holding the version, counts affected attempts and raises an ops alert. Attempts are never rewritten; rescoring is a separate audited decision. A daily session abandoned this way is not reissued for that date.                                                                               | §09 "halt new assignment, flag affected results"; staff cannot write student records under RLS. |
| D-009 | "First encounter" for accuracy = the student's first-ever attempt at a question identity; it counts in the period where it happened. All other attempts are retries, shown separately.                                                                                                                                                                                                                | §10 wording is ambiguous; this avoids counting a retry of an older mistake as a first attempt.  |
| D-010 | Mistakes: a wrong answer creates/updates a `review_items` row due immediately; any later correct answer to that question identity resolves it. Mistake sessions take up to 5 due items (fewer if fewer exist) using the currently published version.                                                                                                                                                  | §10.                                                                                            |
| D-011 | Daily date is computed from the stored timezone. If the most recent daily session's `local_date` is on or after the newly computed date (e.g. after a timezone change), that session is returned instead of issuing another.                                                                                                                                                                          | §10 "prevent an additional challenge for an already-issued local day".                          |
| D-012 | Storage adapter uses the Supabase Storage REST API with the server credential; endpoints must be verified on staging. Local driver is a disk mock with HMAC-signed, expiring URLs served by dev-only routes. Signed URLs expire after 300 s.                                                                                                                                                          | §08.                                                                                            |
| D-013 | Uploaded images: PNG/JPEG/WebP ≤ 2 MB; completion verifies size, SHA-256 and file signature (magic bytes). SVG/HTML are refused.                                                                                                                                                                                                                                                                      | §08.                                                                                            |
| D-014 | Adult freshness: `POST /v1/adult-grants` requires a Supabase `amr` entry with method `otp`/`magiclink` and timestamp ≤ 5 minutes old. Grants are opaque, hashed, single-use, action- and target-scoped, 5-minute expiry. Required for export, deletion and purchase binding.                                                                                                                          | §05.                                                                                            |
| D-015 | RevenueCat adapter reads `GET /v1/subscribers/{app_user_id}` with the secret key and maps records to verified states. The "original transaction identity" is `store:product:original_purchase_date` because the v1 subscriber payload does not expose the store's original transaction id directly. **Verify against the RevenueCat API version in use during sandbox testing before the paid gate.** | §14; spec asks to verify exact APIs.                                                            |
| D-016 | Email delivery ships with a `log` driver only. Parent weekly summaries run only when the `reminders` flag is on and fetch the verified address on demand from Supabase Auth (no email column in our DB). A real provider adapter is required before enabling reminders.                                                                                                                               | §06 "Do not duplicate email unless needed"; §02 reminders may ship after the pilot.             |
| D-017 | `purchase_intents`, `content_imports`, `data_exports`, `deletion_requests`, `analytics_events`, `ops_alerts`, `feature_flags` tables were added; they are implied by spec behaviour but not listed in §06/§07. `attempts` carries denormalized `student_id` and `question_id` for isolation policies and progress queries.                                                                            | §07.                                                                                            |
| D-018 | Per-route rate limits use an in-process limiter (single API instance in V1) plus a global per-IP limit. Replace with a shared store before running multiple API instances. OTP rate limiting is Supabase Auth's.                                                                                                                                                                                      | §16.                                                                                            |
| D-019 | Imports run as a background job (`content.import`) and create drafts authored by the importing staff member; each item uses a savepoint so one bad row cannot abort the batch. Duplicates: same source reference or same content hash.                                                                                                                                                                | §09, §15.                                                                                       |
| D-020 | Free vs Pro: free = daily challenge, explanations, basic progress (14 days of history); Pro = topic practice, mistake-review sessions, 366 days of history. Mistake _list_ is visible to everyone.                                                                                                                                                                                                    | §02.                                                                                            |
| D-021 | Weekly activity goal defaults to 3 completed sessions per ISO week; no streak resets. Rewards: `session_complete` (+10) and `perfect_session` (+5), unique per session.                                                                                                                                                                                                                               | §10 "avoid punitive streak resets".                                                             |
| D-022 | One child profile per account is not enforced; an account can own up to 6 profiles. Entitlements are per child (`entitlements.student_id`), never shared.                                                                                                                                                                                                                                             | §02.                                                                                            |
| D-023 | Withdrawing `core_service` consent revokes every child session for that child. Child sessions can only be issued with active `core_service` consent.                                                                                                                                                                                                                                                  | §05/§16.                                                                                        |
| D-024 | Math renders with KaTeX on web (admin preview) and in a sandboxed, JavaScript-disabled WebView on mobile. Screen readers get the reviewed `alt` text of each math block and image. **Verify on devices against the approved pilot bank's notation.**                                                                                                                                                  | §13.                                                                                            |
| D-025 | Mobile V1 pilot builds do not include the native store SDK. `src/purchases.ts` uses the dev mock store in development and must be replaced with RevenueCat (`appUserID = billingCustomerId`) at the paid gate.                                                                                                                                                                                        | §14, M5.                                                                                        |
| D-026 | Worker shares the API's validated configuration schema (same environment file).                                                                                                                                                                                                                                                                                                                       | Simplicity.                                                                                     |
| D-027 | Unknown/invalid bearer tokens always return 401; a valid child token on a parent/staff route returns 403.                                                                                                                                                                                                                                                                                             | §12 status codes.                                                                               |
| D-028 | Timestamps are serialized as ISO 8601 UTC strings with database precision (connections run with `timezone=UTC`).                                                                                                                                                                                                                                                                                      | §11.                                                                                            |

## Open questions for the project owner (spec §20)

These do not block local implementation:

- Product approval and editorial review owners; which question assets permit reuse.
- Pilot schools/families, whether English-only is sufficient, privacy/consent text approval.
- Hosting accounts and region (backups must meet RPO 24 h / RTO 1 working day).
- Final retention policy (defaults in [security-privacy.md](security-privacy.md)).
- Paid launch: one-child entitlement scope, prices/product ids, countries, store accounts, refund
  and transaction-reassignment policy.
